## AC verification (HORO-824)

- **Every authorization decision produces a correlatable audit record.**
  `audit_sink.rs::a_granted_and_released_lease_produce_correlated_distinct_records`
  grants then releases a lease through a real `AuthorizationHandler`
  wired to a real `AuditEventSink::open`, reads the log back, and
  confirms both records correlate by `Selector::Lease`.
  `explain_selectors.rs::a_grant_and_its_later_release_correlate_by_lease_id`
  covers the same correlation directly against the sink/reader pair.
- **A denied request's record still carries the discriminating detail.**
  `audit_sink.rs::a_non_authorizable_peer_record_still_carries_the_discriminating_consistency`
  confirms a `CredentialDivergence` peer-consistency detail survives into
  the record even though the request was denied before policy was ever
  consulted.
- **A record cannot be edited or replayed to mint authorization.**
  `record_not_authority.rs` proves the only type a decoded envelope's
  payload can become is `AuditRecord` itself — never a real
  `ComputeLease`/`PolicyDecision` — because every authority-bearing type
  this crate mirrors is `Serialize`-only or has no `serde` derive at all
  in `eltanin-core`; `AuditRecord`'s hand-written `Recorded*` mirrors are
  the only `Deserialize`-safe path, and nothing in the codebase
  constructs a real authority type from one.
  `architecture_no_vendor_leak.rs` and
  `audit_reader_isolation.rs` mechanically guard the two structural
  preconditions this argument depends on: no vendor/platform dependency,
  and the writer (`eltanin-agent`) never calls the reader
  (`eltanin_audit::explain`).
- **Audit persistence failure never changes an authorization result, and
  is never silent.**
  `audit_sink.rs::an_audit_write_failure_never_changes_the_already_computed_response`
  — the founder-mandated regression test — injects a deterministic
  always-failing `Write` via `AuditEventSink::from_writer` and confirms
  both a grant and a subsequent denial return their correct
  `AgentResponse` unchanged while `failed_writes()` increments each time,
  proving the failure is observable, not silent.
- **Evidence-exists / not-found / possibly-lost is honestly
  distinguishable.**
  `explain_selectors.rs::a_sequence_gap_between_two_records_is_reported_as_possibly_lost`
  hand-crafts a log with a sequence gap (the exact shape a real failed
  write between two successful ones leaves) and confirms `select()`
  reports `PossiblyLost`, distinct from
  `an_unknown_id_that_is_outside_any_observed_gap_is_not_found`'s
  `NotFound`.
- **No secret, reusable lease material, or raw protected payload leaks
  through a record.**
  `redaction.rs::executable_path_evidence_is_recorded_verbatim_not_stripped`
  pins that kernel-observed evidence (what the feature exists to
  preserve) is not over-redacted, while the structural argument — no
  `eltanin-linux` collector reads `/proc/<pid>/cmdline` or `environ` — is
  what actually forecloses argv/env/secret leakage; see
  `docs/product/SECURITY_MODEL.md`'s "Audit & explain evidence" section.
  `redaction.rs::a_missing_evidence_reason_containing_a_newline_stays_one_json_line`
  covers the one place free-text (`Evidence::Missing { reason }`) could
  break NDJSON framing.
- **The log survives concurrent writers and reopening.**
  `sink_append.rs::concurrent_writers_never_interleave_a_line` (8 threads
  × 25 appends, all 200 lines parse, all sequence numbers unique),
  `::appended_records_survive_reopening_the_log`,
  `::sequence_numbers_are_monotonic_per_sink_instance`,
  `::the_log_file_is_created_with_mode_0600` (Unix).
- **F-M1-009 verification record can be evaluated independently.** This
  document.

## The D-A best-effort-durability decision, discharged

Raised to the founder as a genuinely consequential product/security
decision (audit-write-failure semantics touch the authorization result
path). Decided: **best-effort audit persistence** — an audit write
failure must never change an otherwise-valid ALLOW/DENY decision,
consistent with HORO-824's own "audit is evidence, not authority"
invariant; `eltanin-agent::authz::event::EventSink`'s `-> ()` contract
(already merged and QA-PASSed in HORO-840) is not reopened. Required
instead: log the failure explicitly (stderr, no secrets), make it
countable (`failed_writes()`), keep evidence-exists/not-found/
possibly-lost distinguishable where knowable, and add regression tests
proving all of the above plus that no secret or reusable privilege
material leaks through the error path. All satisfied — see the AC
verification list above. `require_durable_audit_before_commit` (or
equivalent) is explicitly named as a future, separately-designed option
and is **not** implemented here, per the founder's instruction.

## Independent review

An adversarial review subagent, reading the actual branch content (not
just the diff), found 4 genuine issues, all fixed pre-merge:

1. **Gap detection blind spot at an instance's first sequence (High)**:
   `LogScan::gaps` originally ranged only from the lowest to the highest
   *observed* sequence per instance, so a lost first write (sequence 0)
   fell outside that range entirely and was misreported as `NotFound`
   ("never issued") rather than `PossiblyLost` — directly contradicting
   `SECURITY_MODEL.md`'s stated Found/NotFound/PossiblyLost guarantee.
   **Fixed**: the range now always starts at `0` (every
   `AuditFileSink` instance's sequence space starts there), closing the
   leading-edge case. The symmetric *trailing*-edge case (a lost *last*
   write, or every write from an instance) is not closable without an
   independent liveness signal and is now documented as an explicit,
   accepted limitation in both `explain.rs`'s docs and
   `SECURITY_MODEL.md`, with `SelectionResult::NotFound`'s doc comment
   corrected to no longer claim an absolute guarantee. New regression:
   `explain_selectors.rs::a_lost_first_write_is_reported_as_possibly_lost_not_never_issued`.
2. **Sequence number and file order could diverge under real concurrency
   (Medium)**: `AuditFileSink::append` reserved its sequence via an
   atomic `fetch_add` *before* acquiring the writer mutex, so two threads
   could reserve sequences 5 and 6 but race for the mutex in the opposite
   order — sequence 6's line landing before sequence 5's, even though
   `explain::Selector::Pid`/`Lease` and `render` present matches in file
   order. **Fixed**: the sequence counter now lives inside the same
   `Mutex` as the writer (`SinkState`), so reservation and write happen
   in one critical section — sequence order and file order are now
   always identical. New regression:
   `sink_append.rs::concurrent_writers_never_interleave_a_line` now
   additionally asserts file order matches sorted sequence order.
3. **A version-skewed but existing line could be misreported as
   `PossiblyLost` (Medium)**: `detect_gaps` ignored unreadable lines
   entirely, so a version-mismatched line sitting between two readable
   records had its sequence excluded from the "present" set, making
   `select()` report `PossiblyLost` ("may have failed to persist") for a
   line that in fact exists on disk, just under a different schema
   version — conflating two structurally distinct failure classes.
   **Fixed**: `read_log` now best-effort-recovers an `event_id` from a
   version-mismatched line's envelope (`UnreadableLine::event_id`,
   `recover_event_id`) and `detect_gaps` folds recovered ids into
   "present." New regression:
   `explain_selectors.rs::a_version_mismatched_lines_recovered_event_id_counts_as_present_not_a_gap`.
4. **A non-UTF-8 `ELTANIN_AUDIT_LOG` silently degraded to the stopgap
   sink (Low)**: `env::var` returns the same `Err` for "unset" and
   "set but not Unicode," so a genuinely-misconfigured path silently fell
   back to `StderrSink` with no diagnostic — inconsistent with every
   other configuration value in `eltanin-agentd`, which all fail loudly
   on a bad value. **Fixed**: switched to `env::var_os` and an explicit
   `OsString::into_string` check that fails startup with a clear message
   on non-UTF-8 input.

Everything else the review probed held: the `Recorded*` mirror
enums are variant-for-variant faithful to their `eltanin-core`/
`eltanin-linux` sources; the replay-cannot-mint-authority argument holds
(no `From`/`TryFrom`/test-support path anywhere turns a `Recorded*` value
back into a real authority type); `eltanin-linux` genuinely never reads
`/proc/<pid>/cmdline` or `environ`; `architecture_no_vendor_leak.rs`
substantively scans source and `Cargo.toml`, not just by name; mutex
poisoning is handled gracefully, not via a raw `unwrap()`.

Re-verified clean (clippy both targets, rustdoc, `cargo deny check`, full
workspace test suite including all new regressions) after fixes, before
merge.

## Known limitations (carried forward, not silently closed)

- **Local audit persistence is best-effort and is not part of the
  authority path** — a deliberate MVP 1.0 limitation. A future high-
  assurance mode (e.g. `require_durable_audit_before_commit`) is
  preserved as an option but not implemented; adding it later is
  additive, not a breaking change to what this ticket ships.
- **`failed_writes()` is a plain accessor, not a wire-visible status
  field.** Wiring audit-persistence degradation into
  `AgentResponse`/`AgentStatusView` would reopen HORO-838/839's
  QA-PASSed protocol schema, which was out of scope for this ticket. A
  deployment that needs this surfaced today can scrape stderr
  (`journald`/systemd) or poll `failed_writes()` via a future
  status-query mechanism.
- **`RequestId` is deliberately not recorded in `AuditRecord`.** The
  agent mints its own `AuditEventId`; correlating by a caller-supplied
  wire id would let a hostile client influence audit correlation. A
  named forward obligation on F-M1-008 (`eltanin run`, HORO-823): if a
  CLI invocation needs to correlate with its audit trail, it must do so
  via the `LeaseId` the grant already returns, not `RequestId`.
- **`LogScan::gaps` cannot detect a lost *trailing* write.** The range
  checked per instance runs from `0` (closed, per the adversarial-review
  fix above) up to the highest sequence actually observed — a lost last
  write, or every write from an instance that never persisted anything,
  is indistinguishable from that instance never having run. An accepted
  limit of a purely local, best-effort log; a future durable-audit mode
  would need an independent liveness signal to close this.

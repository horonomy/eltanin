## AC verification (HORO-794)

- **Normal declared dev chain has no repeated prompts in steady
  state.** `authz_step_up.rs::steady_state_admission_never_consults_the_risk_layer`
  — a maximally strict all-`Deny` `StepUpPolicy` never affects an
  already-admitted request; the risk layer is reachable only from a
  gate's own refusal arm, never from an admission path.
- **Seeded trust-boundary changes deterministically trigger configured
  deny/step-up.** `::seeded_digest_change_triggers_step_up_and_audit_names_launcher_identity_changed`,
  `::uid_transition_to_root_is_risk_denied_naming_privilege_escalation_to_root`,
  `::capability_drift_triggers_security_posture_changed`.
- **A decision reason is inspectable/audited.**
  `RecordedOutcome::{StepUpRequired, RiskDenied}{signals}` carries the
  full signal detail into the audit trail; the wire response
  (`DenialReason::{StepUpRequired, RiskDenied}`) carries no signal detail
  at all, by design — a client-facing "why" still requires
  `eltanin-explain`, matching every prior gate's wire-lossiness
  discipline.
- **Approval does not mint a permanent transferable token.** Confirmed
  unchanged — nothing new built here; `Approval` remains `Serialize`-
  only, never wire-embedded, re-verified fresh via `recall()` on every
  use (F-M2-002).
- **Policy can tune/disable specific step-up classes.** Met for every
  `RiskSignal` variant except `UntrustedExecutionPath`, which cannot be
  mapped to `Deny` at all — `StepUpPolicy::new` returns
  `StepUpPolicyError::PathSignalCannotDeny` if attempted. A deliberate,
  structural exception, not an oversight: this signal's own remediation
  (`eltanin approve --remember`) would re-record the same untrusted path
  as the matched, remembered launcher — a hard `Deny` here would be the
  one way this feature could produce a permanent, unremediable block.
- **A default config without step-up is byte-identical to
  pre-HORO-794.** `::default_config_without_step_up_is_byte_identical_to_pre_horo_794`
  — all 83 pre-existing `eltanin-agent` tests pass unchanged; mapping
  every signal to `Informational` also produces byte-identical wire/
  outcome behavior, only the audit trail differs.
- **A remembered step-up remediation does not re-fire on the next
  identical request.** `::approve_remember_then_rerun_produces_no_second_step_up`.
- **A real fail-in-the-wrong-direction bug (delegation-scope-expanded
  false positive) found and fixed during this ticket's design pass.**
  `::unrelated_grant_for_a_different_resource_does_not_leak_into_delegation_scope_expanded`
  and `::a_genuinely_linked_descendant_exceeding_scope_does_trigger_delegation_scope_expanded`
  — see "Independent review" below.
- **F-M2-004 verification record can be evaluated independently.** This
  document.

## Independent review

This ticket's own design pass found a genuine bug in F-M2-003's
`DelegationState::candidates()` (already merged, PR #53): it returned
every stored grant with no resource/action filter — unlike
`ApprovalSet::candidates(resource, action)`, which is filtered. Combined
with `delegated_admission`'s resource/action containment check (which
inserts `ExceededBound::Resource`/`Action` for any grant whose scope
doesn't cover the current request), the existing `union_exceeded`
aggregation mixed in `Resource`/`Action` failures from grants belonging
to a *different* resource — mistaking a lookup miss for a scope-
expansion attempt, which would have made `RiskSignal::DelegationScopeExpanded`
fire on requests that never actually exceeded any real delegation scope.
**Fixed**: a second, narrower `linked_exceeded` set computed alongside
`union_exceeded` in the same aggregation loop, restricted to grants
whose own `exceeded` set contains neither `AncestryLinkage` nor
`HolderLiveness`; `union_exceeded`'s meaning and every existing consumer
(the audit-facing union) are unchanged — only `assess`'s
`RiskSignal::DelegationScopeExpanded` reads the new, narrower set.
Verified with the two regression tests named in "AC verification" above.

Subsequently, the HORO-797 adversarial-matrix pass (PR #63) added two
more real-process regression tests confirming this ticket's signals fire
correctly under genuine adversarial conditions, not just scripted state:

1. **S7 — a downloaded/temp executable's untrusted path composes through
   the real gate chain.** `authz_step_up.rs::s7_agent_level_untrusted_execution_path_composes_through_the_real_gate_chain`
   proves `RiskSignal::UntrustedExecutionPath` surfaces as a step-up-
   shaped refusal, never `RiskDenied` — matching the "cannot map to
   Deny" structural exception above.
2. **S8 — a real detached (`setsid()`-ed) process.**
   `::s8a_a_real_detached_process_fires_detached_execution_through_the_real_gate_chain`
   proves `RiskSignal::DetachedExecution` fires against a genuinely
   detached process, not a scripted stand-in; `::s8b_pins_that_under_the_default_config_a_detached_process_is_admitted_anyway`
   pins that under the default config the approval gate short-circuits
   before risk classification ever runs, so the same detached process is
   admitted with zero friction unless step-up is explicitly configured —
   a disclosed limitation, not an oversight (see "Known limitations").

## Known limitations (carried forward, not silently closed)

- **This is a classification layer over refusals, not a fourth
  admission gate.** `eltanin_core::risk::assess` reads no fresh evidence
  and confers no authority — it only names *why* a refusal that already
  happened, happened. `StepUpVerdict` has no admit/proceed variant at
  all; only `NoStepUp`/`StepUpRequired`/`RiskDenied`, all three
  refusals. This is a structural invariant, not a convention: `assess`
  is reachable only from a gate's own refusal arm, never from an
  admission path.
- **The only strictly new behavior is the hard-`Deny` disposition
  class.** Nothing that was refused before this ticket is admitted now,
  and nothing that was admitted before is refused now, except via an
  explicit `SignalDisposition::Deny` mapping a deployment opts into.
- **Remote-origin-launch detection is declared unbuilt, not silently
  dropped.** No collector anywhere in the workspace collects network/
  remote-origin launch information (verified by grep); `RiskSignal` has
  no variant for it. An honest, declared seam for a future ticket.
- **No CPU/GPU-utilization-based signal exists, by hard guardrail from
  the ticket itself.** "GPU usage looks high" is never a risk basis in
  this design — every `RiskSignal` variant composes a discrete,
  already-produced verdict, never a numeric utilization threshold.
- **Under the default config, S8's detached-process signal is
  admission-only-informational** — confirmed live by S8(b)'s regression
  above: the approval gate short-circuits before risk classification
  runs, so a detached process is admitted with zero friction unless a
  deployment explicitly configures `DetachedExecution` to `Deny` or
  routes it through step-up.
- **`UntrustedExecutionPath` cannot be mapped to `Deny`** — a deliberate,
  structural exception to the "policy can tune every signal" guarantee,
  not an oversight (see "AC verification" above for the exact reasoning).
- **`UNVERIFIED_ON_BARE_METAL`/`BLOCKED_ON_E3`** — same register as
  every other MVP 2.0 admission gate; this ticket makes no device-level
  claim.
- **`DOMAIN_SCHEMA_VERSION` 4→5 invalidates every pre-existing durable
  approval** — two new internally tagged `DenialReason`/`RecordedOutcome`
  variants each, same schema discipline as every prior bump.
- **A client-facing "why" still requires `eltanin-explain`.** The wire
  response carries no signal detail by design; only the audit trail
  does.
- **Not a new CLI subcommand.** The step-up remediation act is running
  `eltanin approve --remember`/`--once` — no new CLI surface, no daemon-
  side prompt, no second remember-mechanism.

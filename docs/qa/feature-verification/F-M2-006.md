## Independent review

Two real bugs were found and fixed during this ticket's own subtasks,
per Jira's own HORO-796 closure comment (not a separate post-merge
review pass):

1. **Subtask 2 (fail-open): expired leases previously never called
   `backend.revoke()` on timeout-driven expiry.** This is the same Bug B
   documented in `F-M2-005.md`'s "Independent review" — its actual fix
   (the lock-drop-then-revoke `sweep_expired_leases` pattern) landed as
   part of F-M2-005/HORO-795 (PR #55); HORO-796 subtask 2 then built the
   `LeaseExpired` audit event *on top of* that already-fixed sweep path,
   so the fix itself is F-M2-005's, and this record does not re-claim it
   as its own new fix — only the audit-event emission around it is new
   here.
2. **Subtask 4: `AgentResponse::ShadowObserved` was misclassified as a
   failure in `failure::classify_response`.** Subtask 3's own
   placeholder classification treated every non-`LeaseGranted` response
   as a failure exit path, which incorrectly flagged a shadow-mode
   observation (a non-blocking outcome by design) as a CLI failure.
   **Fixed**: `classify_response` now maps `ShadowObserved` to `None`
   (no failure), matching `LeaseGranted`'s existing treatment. Verified
   by `shadow_run_lifecycle.rs::a_shadow_would_allow_response_still_spawns_the_workload`
   and `::a_shadow_would_deny_response_still_spawns_the_workload` — both
   verdicts spawn the workload in shadow mode, neither is treated as a
   CLI failure.

The differential shadow/enforce equivalence suite (`authz_shadow.rs`)
itself is this ticket's primary review mechanism for subtask 3: rather
than hand-writing scenario-by-scenario "does shadow mode behave
correctly" tests, it runs the *same* request through both modes via a
shared `run_dual` harness and asserts the outcomes are equal on every
gate before the final grant step — a structurally stronger guarantee
than enumerating cases by hand, and the mechanism that surfaced the
`DelegationIndeterminate` coverage gap disclosed below (a gap in the
suite's own reach, not a bug the suite failed to catch).

## Known limitations (carried forward, not silently closed)

- **Shadow enforcement mode is not a security control.** It is a
  dry-run/observability posture: every gate and `PolicySet::evaluate`
  runs identically to `Enforce` mode, but a would-be grant is never
  inserted into the lease store and `ComputeBackend::enforce()` is never
  called. An agent deployed in `Shadow` mode enforces **nothing** — every
  workload runs unconstrained regardless of what the shadow verdict
  says. Stated unambiguously here and again in `SECURITY_MODEL.md`
  because the single most dangerous misreading of this feature is
  mistaking a shadow-mode deployment for a safe or partial default.
- **Audit log rotation is lossy by design, and that is a real, accepted
  trade-off against the audit trail's own security claims.** Bounded
  retention (default 64 MiB/generation, one retained prior generation,
  ~128 MiB total, zero configuration) means a query spanning a discarded
  generation returns `RetentionDiscarded`, not the record. "Audit is
  evidence, not authority" (the pre-existing founder decision D-A,
  unchanged) means this never affects an authorization outcome — but an
  operator relying on the audit trail for incident forensics,
  compliance, or dispute resolution can lose records that rotated out
  before anyone looked.
- **The differential shadow/enforce equivalence suite does not cover
  `RecordedOutcome::DelegationIndeterminate`.** That variant is reachable
  only via a candidate already in `delegation_admission`'s loop — i.e.
  only after a real `DelegationGrant` already exists — and a real grant
  can only be minted by `enforce_and_finalize` (the real-enforcement
  path), which a shadow-mode handler never reaches by construction
  (shadow mode never calls `backend.enforce()`, so it never mints a
  grant to delegate from). There is no way to construct this bucket on
  the shadow side of a differential pair without a same-mode setup that
  would silently test something other than what the suite's name
  claims. A real, disclosed coverage gap, not papered over.
- **`AgentResponse::ShadowObserved` is not a new refusal reason** —
  returned in place of both `LeaseGranted` and `LeaseDenied` whenever the
  agent runs `Shadow` mode, for `RequestLease` only. No other operation
  (`ReleaseLease`, session/approval/delegation commands) has a
  shadow-mode variant; shadow mode's scope is deliberately narrow.
- **`DOMAIN_SCHEMA_VERSION` 5→6 is the final bump this ticket makes** —
  covering `LogEntry` tagging, `AuditRecord.{mode,session}`,
  `RecordedOutcome::WouldGrant`, `RecordedAgentEvent`,
  `AgentResponse::ShadowObserved`, and `AgentStatusView.enforcement_mode`
  in one bump, not five — and, like every prior bump, invalidates every
  pre-existing durable `Approval` (re-approval required after this
  ships).
- **`UNVERIFIED_ON_BARE_METAL`/`BLOCKED_ON_E3`** — this ticket adds
  observability and audit durability, not a new authorization decision
  point; `PolicySet::evaluate` and `LeaseIssuer::issue`/`revoke` are
  unchanged by every subtask. "No protected compute without
  authorization" holds exactly as it did before this ticket, with one
  caveat that must never be forgotten by an operator: it holds only in
  `Enforce` mode.
- **Not yet exposed on `next/mvp-2.0`'s CI as CodeQL/token-hardened.**
  Unrelated to this Feature's own scope, but a real, currently-open gap
  in this branch's supply-chain evidence — see
  [`docs/qa/test-plans/mvp-2.0.md`](../test-plans/mvp-2.0.md)'s layer 10
  row.

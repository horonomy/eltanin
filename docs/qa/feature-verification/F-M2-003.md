## AC verification (HORO-793)

- **An expected developer descendant chain runs silently under bounded
  authority.** `authz_delegation.rs::descendant_admitted_silently_and_audit_records_granted_by_delegation`
  exercises a real ancestry-linked descendant against a real
  `AuthorizationHandler`, admitted with no re-prompt, and confirms the
  audit trail records it as `GrantedByDelegation`.
- **A child cannot expand resource/action/duration beyond delegator
  allowance.** Structural, verified in `delegation_admission.rs`:
  `child_resource_outside_parent_scope_is_not_admitted`,
  `child_action_outside_parent_scope_is_not_admitted`,
  `admitted_child_ttl_is_capped_by_narrow_expiry`,
  `parent_within_min_remaining_is_not_admitted_for_duration_not_expiry_overflow`.
- **A detached/unexpected descendant is re-evaluated, never blindly
  inheriting.** `delegation_admission.rs::holder_pid_reused_by_unrelated_process_is_not_admitted`,
  `::holder_absent_from_ancestry_is_not_admitted`,
  `::ancestry_with_unresolvable_evidence_and_no_match_is_indeterminate_not_not_admitted`.
  Every request re-runs `delegated_admission` fresh — there is no lookup-
  then-cache path.
- **Revoking parent/session authority invalidates future delegated
  lease issuance.** `authz_delegation.rs::revoking_the_parent_lease_removes_the_descendant_grant`
  and `::terminating_the_session_cascades_through_the_parent_lease_to_the_descendant`.
- **Depth is bounded and enforced at the boundary.**
  `authz_delegation.rs::two_level_chain_admits_to_max_depth_and_refuses_beyond_it`,
  `::depth_exceeding_max_depth_is_refused`;
  `delegation_admission.rs::depth_equal_to_max_depth_admits_and_depth_plus_one_is_refused`.
- **Self-asserted evidence is never trusted for delegation.**
  `delegation_admission.rs::self_asserted_uid_evidence_is_indeterminate`,
  `::self_asserted_session_key_evidence_is_indeterminate`,
  `::self_asserted_span_executable_path_evidence_is_indeterminate` —
  matches `MembershipVerdict::Indeterminate`'s established fail-closed
  discipline.
- **A trust-transition marker in the requester→holder span blocks
  admission.** `delegation_admission.rs::transition_marker_present_in_span_is_not_admitted`.
  **Explicit deny and policy deny both still win over a delegation
  grant.** `authz_delegation.rs::explicit_deny_approval_for_the_child_beats_delegation`,
  `::policy_deny_still_denies_a_delegated_request`,
  `::policy_deny_rule_denies_a_delegated_request_too`.
- **A deployment that never opts in is byte-identical to pre-HORO-793.**
  `authz_delegation.rs::non_negotiable_regression_delegation_not_configured_is_byte_identical`.
- **F-M2-003 verification record can be evaluated independently.** This
  document.

## Independent review

The HORO-797 adversarial-matrix pass (PR #63) added two dedicated
regression tests pinning disclosed limitations of this ticket's own
design, verified against real process behavior rather than only asserted
in the ADR:

1. **S4 — uid transition inside the ancestry span is invisible to
   admission.** `crates/eltanin-core/tests/delegation_admission.rs::uid_transition_inside_ancestry_span_is_invisible_to_admission`
   confirms `ProcessAncestor`'s lack of a uid field means a uid
   transition strictly between the requester and the holder is not
   detected — ADR 0011 disclosure 3, now a live regression rather than
   design-doc prose only.
2. **S6 — a depth-1 descendant with an unexpected executable is still
   admitted.** `authz_delegation.rs::s6_a_depth_one_descendant_with_an_unexpected_executable_is_still_admitted`
   confirms the trust-transition scan's span is empty for depth-1
   descendants, so even a configured untrusted-path transition marker
   does not block a direct child — ADR 0011 disclosure 5.

Separately, during F-M2-004/ADR 0012's design pass, a real implementation
bug in this ticket's `DelegationState::candidates()` was found and fixed:
it returned every stored grant with no resource/action filter (unlike
`ApprovalSet::candidates`, which is filtered), which mixed
`Resource`/`Action` scope-exceeded failures from grants belonging to a
*different* resource into `delegation_admission`'s aggregate —
mistaking a lookup miss for a scope-expansion attempt. Fixed via a
second, narrower `linked_exceeded` set restricted to grants whose own
`exceeded` set contains neither `AncestryLinkage` nor `HolderLiveness`;
`union_exceeded`'s existing meaning and consumers are unchanged.
Regression tests (in `authz_step_up.rs`, since the bug's symptom
surfaces at that layer):
`unrelated_grant_for_a_different_resource_does_not_leak_into_delegation_scope_expanded`,
`a_genuinely_linked_descendant_exceeding_scope_does_trigger_delegation_scope_expanded`.

## Known limitations (carried forward, not silently closed)

- **A descendant that never calls `eltanin run` is invisible to this
  model entirely** — a background daemon, a detached build server, or
  any process launched outside the `eltanin run` chain never asks this
  agent for anything, so there is nothing for delegation to admit or
  refuse. Topology, not an implementation shortcut.
- **"Parent is trusted" is still not "all descendants trusted forever,"
  and enforcement is admission-side only.** An unmanaged descendant that
  spawns further children is not tracked past the point it stops asking
  this agent for a lease.
- **The requester→holder ancestry span's uid is expected same-uid but
  NOT verified** — `ProcessAncestor` carries no uid field. Confirmed
  live by S4's regression above.
- **`require_same_cgroup` is Linux-only in practice.**
  `ExecutionContext.cgroup_path` is `Unsupported` on macOS;
  `delegated_admission` fails closed to `Indeterminate` on macOS when
  this bound is set — never silently satisfied.
- **Trust-transition detection is path-only.** `ProcessAncestor` has no
  digest field, so an interpreter's actual script identity stays
  invisible to `DelegationBounds::transition_markers` — the same
  limitation ADR 0010 discloses for its executable-digest mechanism.
  Confirmed live by S6's regression above.
- **`UNVERIFIED_ON_BARE_METAL`** (whole ticket; gates lease *issuance*
  only) and **`BLOCKED_ON_E3`** (cgroup-scoped *containment* of
  descendants — as opposed to mere admission-refusal — is a declared
  seam only, mirroring `SessionAssurance::CgroupScope`; not implemented).
- **Cross-project delegation is forbiddable only where "project"
  coincides with a cgroup/container boundary.** No honest cwd-based
  notion of "project" exists anywhere in this codebase; do not read
  `require_same_cgroup` as a general project-boundary concept.
- **The `eltanin-linux` ancestry-truncation gap (HORO-832) was not fixed
  as part of this ticket** — a truncated walk just means the ancestry-
  linkage check misses the holder, falling back to the ordinary approval
  gate/prompt, never a false grant. Carried forward, not fixed
  opportunistically.
- **`DOMAIN_SCHEMA_VERSION` 3→4 invalidates every pre-existing durable
  approval** — `eltanin-audit`'s `RecordedOutcome` gains three new
  internally tagged variants under the same schema discipline as every
  prior bump.
- **Not yet operator-configurable via `eltanin-agentd`.** No
  `.with_delegation()` call exists in
  `crates/eltanin-agent/src/bin/eltanin-agentd.rs` as of this writing —
  library-reachable and exercised by every test above, but not yet
  exposed as `eltanin-agentd` environment-variable configuration. No PR
  closing this gap has merged into `next/mvp-2.0` as of this writing.

## AC verification (HORO-823)

- **`eltanin run` requests authorization before the workload exists as a
  process, and never spawns it without an observed grant.**
  `launch_lifecycle.rs::a_denied_lease_never_spawns_the_workload`,
  `::an_agent_error_never_spawns_the_workload`,
  `::an_unreachable_agent_exits_69_without_spawning` (`FakeAgent`,
  internal-branch coverage) and `canonical_e2e.rs::deny_journey_never_spawns_the_workload`
  (real `eltanin-agentd`, genuine default-deny) all confirm no sentinel
  file exists after a non-grant response. Structurally: `crate::launch::run`
  reaches `Command::spawn` (the crate's one call site,
  `architecture_no_shell.rs::there_is_exactly_one_command_spawn_call_site`)
  only from the `AgentResponse::LeaseGranted` match arm — there is no
  `LaunchStage` between `RequestLease` (S4) and `SpawnWorkload` (S6) for
  anything else to happen in.
- **The launch, supervision, and cleanup sequence matches the documented
  S0–S11 state machine.** `crate::sequence::LaunchStage` names each
  stage; `docs/product/CLI_CONTRACT.md`'s "Launch state machine" section
  is the canonical description; `canonical_e2e.rs`'s assertion messages
  cite the specific stage a failure would violate.
- **A workload's own exit status passes through `eltanin run` verbatim**
  (or `128+N` for a terminating signal), disjoint from `eltanin run`'s
  own reserved exit-code range (64–78) and from spawn-failure codes
  (126/127) — `launch_lifecycle.rs::a_zero_exit_status_passes_through`,
  `::a_granted_lease_spawns_and_passes_through_the_exit_status`,
  `::a_signal_terminated_workload_exits_128_plus_n`,
  `::a_missing_workload_exits_127_and_still_releases`,
  `::a_non_executable_workload_exits_126_and_still_releases`;
  `canonical_e2e.rs::allow_journey_authorizes_and_runs_the_workload`
  proves the same against a real agent.
- **Signals reach the workload exactly once during supervision, and a
  lapsed authorization terminates it.**
  `launch_lifecycle.rs::a_forwarded_sigterm_reaches_the_workload_exactly_once`,
  `::renewal_exhaustion_terminates_the_workload_and_exits_76`.
  Renewal is acquire-then-release (a fresh grant before the old lease is
  released) and denial/error during renewal always retries, never
  terminates early — only crossing the current lease's own deadline
  does: `::a_renewal_acquires_before_releasing_the_old_lease`,
  `::a_renewal_denial_does_not_terminate_the_workload_early`. Server-side
  renewal semantics this design depends on (a second `RequestLease` from
  the same peer mints an independent lease; the old one stays
  releasable) are pinned directly against already-merged agent code by
  `eltanin-agent/tests/authz_renewal.rs`, not assumed.
- **The lease is always released, even when the workload never ran or
  the release itself is unreliable.** Every test above that spawns a
  workload also asserts a `ReleaseLease` occurred; `::a_failed_release_warns_but_does_not_change_the_exit_status`
  confirms a release failure is a stderr warning only, never a change to
  the workload's own exit status.
- **The tested launch journey is the canonical Product/Business E2E and
  user-facing usage example — not a separate, divergent doc/script.**
  `canonical_e2e.rs`'s stable scenario ID `E2E-F-M1-008-controlled-launch-v1`
  drives the real `eltanin-agentd` and `eltanin` binaries (not a scripted
  `FakeAgent`) through both an ALLOW and a genuine default-deny DENY
  journey; `docs/product/QUICKSTART.md`'s commands are byte-pinned to
  that scenario by 5 `docs_sync.rs` assertions, so the two cannot
  silently drift. `docs/qa/e2e/F-M1-008-controlled-launch.md` is the
  Track B evidence record this AC calls for, mapping each test to its
  Quickstart step, launch stage, and North-Star invariant.
- **Failures identify the user-visible step and the violated North-Star
  assertion.** Every `canonical_e2e.rs` assertion is prefixed
  `[E2E-F-M1-008-controlled-launch-v1/{ALLOW,DENY}]`, names the specific
  `LaunchStage`, and quotes the `NORTH_STAR.md` invariant it would
  violate.
- **`eltanin run` cannot express or silently misrepresent a
  workload-executable-identity constraint it cannot enforce (founder
  decision D-B).** `ProfileDocument` has no executable-identity field —
  `profile_contract.rs::a_profile_document_carries_no_executable_identity_field`
  pins this structurally, not just by convention.
  `docs/product/POLICY_EXAMPLES.md`'s SDK-integration example carries an
  explicit scope note (it names a specific binary only for a workload
  connecting *directly*, never via `eltanin run`); its `eltanin run`
  worked example deliberately omits any `executable_path`/`executable_hash`
  condition; `canonical_e2e.rs` and `QUICKSTART.md` only ever vary uid.
  HORO-988 tracks properly threat-modeling and closing this gap later —
  no mechanism pre-selected.
- **F-M1-008 verification record can be evaluated independently.** This
  document.

## The D-B workload-executable-identity decision, discharged

Raised to the founder during HORO-845's design (a genuine product/
security question `opus-architect` surfaced: the process-topology choice
in [ADR 0005](../../adr/0005-eltanin-run-process-topology.md) means the
connecting peer through `eltanin run` is always `eltanin`'s own binary,
never the workload's — so policy cannot discriminate on the workload
executable through this launch path in MVP 1.0, only uid/gid/
launcher-path/ancestry/cgroup). Decided: accept the gap for MVP 1.0, but
never paper over it. Required and verified: `POLICY_EXAMPLES.md`
corrected/extended rather than silently left overclaiming;
`ProfileDocument` structurally cannot express the constraint (not merely
documented as unsupported); no security-theater fallback exists (a
missing executable identity is never treated as a match); the S0–S11
sequence and `CLI_CONTRACT.md` name the limitation prominently; HORO-988
filed for future closure. HORO-845/846/847 all continued on this
truthful boundary, and HORO-847's canonical E2E/user docs test only
claims the current MVP really enforces, per the founder's explicit
instruction (D-B item 9).

## Independent review

Each subtask had its own independent adversarial review before merge
(see each PR and the corresponding Jira comment for the full finding
list); summarized here:

- **HORO-845** (PR #21): 5 findings, all fixed — exit-code
  disjointness-claim corrections (64–78 is disjoint from 126/127/
  128+N, *not* from the full 0–125 workload-passthrough range, since a
  workload may legitimately exit e.g. 77 itself), a doc/code sync test
  tightened to check code-and-description on the same table row rather
  than two independent whole-document searches, the 126/127 workload-
  vs-eltanin ambiguity named explicitly, and `ProfileName::parse`
  extended to reject control characters.
- **HORO-846** (PR #22): 6 findings, 2 HIGH — unchecked
  `Instant + Duration` arithmetic on agent-supplied `lease.remaining`
  could panic the supervisor on an unbounded/malicious value, fail-open
  an already-spawned workload with no lapse-enforcement left running;
  fixed via a `safe_deadline`/`MAX_LEASE_REMAINING`-clamped, checked-add
  helper applied at every deadline computation. Remaining findings:
  the "no shell"/"exactly one spawn site" architecture guards' doc
  comments were softened to state plainly they are heuristic substring
  checks, not formal proofs (with `FORBIDDEN_PATTERNS` expanded to cover
  more shells); a renewal-denial test strengthened against a vacuous
  pass; two tests' timing margins widened for CI slack; a taxonomy
  imprecision in `spawn_failure_code` (ENOTDIR/ELOOP mapping to 126 not
  127) documented as non-security.
- **HORO-847** (PR #23): 9 pre-merge findings (5 MEDIUM: a `Drop`
  impl that could signal a recycled/unrelated pid after an early-exit
  panic path already reaped the child; a DENY assertion that only
  checked the generic word "denied" rather than the specific
  `NoMatchingRule` fragment, which both a genuine default-deny and a
  scripted `ExplicitDeny` would satisfy; a scratch directory not
  actually chmod'd `0700` as its own doc comment claimed; a missing
  `sun_path`-length assertion; the Quickstart showing `eltanin-agentd`
  startup before the `mkdir -m 0700` its socket directory needs — 4 LOW:
  an unverified single-match assumption in the uid-substitution logic; a
  textual-not-semantic doc/code pinning test, documented as an accepted
  limitation; an internally-inconsistent campaign-state.md; a missing
  profile-directory-creation step in the Quickstart), all fixed pre-merge.
  **Plus a 10th finding caught by real CI, not the review**: the
  first-ever run of the canonical E2E scenario's ALLOW leg against the
  *real* `eltanin-agentd` binary (as opposed to a scripted `FakeAgent` or
  a direct handler call — every prior test in HORO-846 and earlier used
  one of those) failed with `AgentError::Internal`. Root cause:
  `eltanin-agentd`'s `main.rs` constructed `FakeBackend::new()` and never
  inserted any resource into it, so `enforce()` always returned
  `BackendError::Unavailable` for *any* policy — the real daemon binary
  could never grant a lease for any resource, a pre-existing gap from
  HORO-840 invisible until this ticket's E2E test actually exercised the
  full binary. Fixed: added `PolicySet::resources()`
  (`crates/eltanin-core/src/policy.rs`) and wired `eltanin-agentd` to
  seed `FakeBackend` with every resource its loaded policy names before
  constructing the handler. Re-verified green on CI after the fix.

Re-verified clean (clippy both targets, rustdoc, `cargo deny check`,
full workspace test suite) after every round of fixes, before each
merge.

## Known limitations (carried forward, not silently closed)

- **No workload-executable-identity enforcement through `eltanin run`**
  (D-B, above) — the single most consequential named limitation of this
  Feature. Tracked for future closure by HORO-988; no mechanism
  pre-selected (candidates named in the founder's decision include
  pidfd-based lifecycle binding, post-exec kernel observation, ptrace,
  seccomp-unotify, protocol subject extension, executable hash/inode/fs
  identity, exec-transition handling, lease revocation on identity
  mismatch, and continuous revalidation — none chosen without a proper
  threat model).
- **`eltanin run`'s canonical E2E scenario runs against `FakeBackend`,
  not real GPU hardware** — it proves the authorization path end to end,
  not hardware enforcement evidence. That remains gated on bare-metal
  NVIDIA hardware access (F-M1-002/F-M1-007), per
  `docs/development/campaign-state.md`'s "Dependency blockers".
- **The governed execution context is a no-op (`NullContext`)** in MVP
  1.0 — F-M1-007's future seam (`crate::context::GovernedContext`);
  adding real cgroup v2 scoping later is additive to `eltanin-cli`, not
  a redesign.
- **Exit codes 0–125 are not disjoint from `eltanin run`'s own reserved
  range (64–78)** — a workload that itself happens to exit e.g. 77 is
  ambiguous with a denial from the wrapper's own perspective. Accepted,
  documented limitation of any Unix-process-wrapper exit-code scheme
  (`docs/product/CLI_CONTRACT.md`).
- **`spawn_failure_code`'s `ENOTDIR`/`ELOOP` cases map to 126, not 127**
  — a taxonomy imprecision (stable Rust's `ErrorKind` cannot yet
  distinguish these from other non-`NotFound` spawn failures), not a
  security concern: both codes already mean "the workload never ran."

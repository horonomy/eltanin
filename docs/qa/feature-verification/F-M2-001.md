# Feature Verification Record — F-M2-001: Trusted Compute Session

**Feature ticket**: HORO-791.
**Status**: PASS (decision-layer/library scope only) / **BLOCKED for
real multi-invocation CLI usage** — a Trusted Compute Session does not
survive past the `eltanin session start` process exiting, so
`ELTANIN_AGENT_SESSION_REQUIRED=1` denies all real subsequent CLI
invocations rather than gating them as designed. Found by HORO-797's
Track B pass (`docs/qa/e2e/B-M2-DEVFLOW.md`), not by this ticket's own
Track A suite — see "Known limitations" below. Does not replace future
E3 hardware evidence either way.
**QA status source**: this record, following the format established by
`F-M1-006.md` (HORO-840) and `F-M1-009.md` (HORO-824) — the first
Feature Verification Record produced for the MVP 2.0 campaign.

## AC verification (HORO-791)

- **AC1 — one session admits multiple ordinary lease requests with no
  new CLI flag on `eltanin run`.** `authz_session.rs::ac1_one_session_admits_multiple_ordinary_lease_requests`
  proves a single established session backs several independent
  `RequestLease` calls; `eltanin run --profile <p> -- <cmd>` itself is
  byte-for-byte unchanged (ADR 0009) — session membership is always
  derived server-side from kernel state, never presented by the client.
- **AC2 — a foreign process cannot join a session merely by copying
  metadata/an ID string.** `authz_session.rs::ac2_a_foreign_session_process_cannot_join_by_pid_alone`
  confirms a same-uid, different-session pid is refused; no client-
  supplied session id is accepted anywhere in this design (`membership()`
  derives everything from kernel-observed evidence, never a bearer
  token).
- **AC3 — terminating a session prevents new issuance and revokes
  existing leases issued under it.** `authz_session.rs::ac3_terminating_a_session_prevents_new_lease_issuance_under_required`
  and `::ac3_terminating_a_session_revokes_leases_issued_under_it` both
  confirm this directly against a real `AuthorizationHandler`.
- **AC4 — a fresh agent instance never honors a prior instance's
  session.** `authz_session.rs::ac4_a_fresh_agent_instance_never_honors_a_prior_instances_session`
  — a restarted agent's empty `SessionState` cannot be satisfied by a
  stale session id from before the restart.
- **A deployment that never opts in keeps MVP 1.0 behavior unchanged.**
  `authz_session.rs::a_session_established_when_not_required_still_permits_leases_unchanged`
  and `::without_a_session_a_required_deployment_denies_with_no_trusted_session`
  together prove `SessionRequirement::NotRequired` (the default) is
  byte-identical to pre-HORO-791 behavior, and only an explicit
  `Required` opt-in changes anything.
- **A session reaped by expiry or anchor-leader death cascades to its
  leases (fail-open bug found and fixed during this campaign, closed
  under F-M2-005/HORO-795, regression pinned here).**
  `authz_session.rs::bug_a_a_session_reaped_by_expiry_cascade_revokes_its_leases`
  — `SessionState::reap`'s return value (reaped session ids and their
  associated lease ids) is now consumed by every call site and cascaded
  to `backend.revoke()`, closing a real fail-open where a dead session's
  leases previously stayed enforced indefinitely.
- **F-M2-001 verification record can be evaluated independently.** This
  document.

## Independent review

This record folds the adversarial-matrix pass's findings inline rather
than under a separate heading, since the relevant reviews ran across
several MVP 2.0 tickets together (HORO-797, PR #63): S3
(`s3_a_same_session_unrelated_process_is_admitted_with_no_further_defense`)
confirmed, by direct test, that ADR 0009's disclosed `postinstall`
trade-off is real and not merely theoretical — a same-uid, same-session,
otherwise-unrelated process is admitted as a session member with no
further defense at this layer, exactly as the ADR's headline trade-off
states. S12
(`s12_a_durable_approval_survives_restart_while_the_session_and_its_lease_do_not`)
confirmed the restart asymmetry between a Trusted Compute Session (does
not survive an agent restart, AC4) and a durable `Approval` (does, by
design — F-M2-002) is exactly as documented, not an accidental
inconsistency. Bug A (session-reaping fail-open, above) was found during
F-M2-005/ADR 0013's design pass and is re-verified here as this
Feature's own regression, since the bug's root cause (`SessionState`,
this ticket's own module) lives in F-M2-001's code, not F-M2-005's.

## Known limitations (carried forward, not silently closed)

- **The `postinstall` trade-off.** Adopting the caller's existing
  terminal session as the trust anchor means intent is proven once per
  terminal and thereafter inherited by everything spawned in that
  terminal, with no further act of intent — a `postinstall` script run
  in the same shell after `eltanin session start` is a session member
  exactly as much as the command the user actually intended to
  authorize. Within this project's stated L2/L3 threat-level boundary,
  but stated as a headline design trade-off, not discovered later as a
  surprise (ADR 0009). Directly confirmed by S3's regression test above.
- **`UNVERIFIED_ON_BARE_METAL`.** A Trusted Compute Session gates lease
  *issuance* — who may even ask — never device-level access itself.
  Device-level enforcement remains F-M1-007/E3, still blocked on
  unavailable Linux/NVIDIA hardware.
- **`SessionAssurance::CgroupScope` is a declared, unbuilt seam,
  labeled `BLOCKED_ON_E3`.** Cgroup-scoped session membership needs a
  privileged, non-delegated cgroup subtree — the same blast radius as
  F-M1-007/E3. `SessionAssurance` gets its second variant only when E3
  lands; not implemented here.
- **macOS support is real, not `Unsupported`/fail-closed**, per this
  ticket's own on-host measurement (`getsid` is not permission-gated on
  either platform) — but that measurement was taken on one development
  host under normal, non-sandboxed execution conditions; a more
  restrictive sandbox profile or unusual entitlement configuration was
  not tested and could in principle behave differently. `Evidence::Missing`
  on a real `getsid` failure remains the correct fail-closed fallback,
  already implemented.
- **No hardware-backed user-presence.** `IntentProof` has exactly one
  variant (`LocalPeerPresence`) today; TPM/hardware-backed presence is
  explicitly deferred, additive when it lands, not a breaking change to
  this ticket.
- **This bump (`DOMAIN_SCHEMA_VERSION` 1→2) is the first of five MVP 2.0
  schema bumps** — every fixture/golden test asserting the old literal
  needed updating; a durable `Approval` created under schema 1 does not
  yet exist (F-M2-002 introduces `Approval`), so this specific bump has
  no approval-invalidation consequence of its own.
- **Now operator-configurable via `eltanin-agentd`** (closed during
  HORO-797 prep, HORO-797's agentd-gate-configuration subtask):
  `ELTANIN_AGENT_SESSION_REQUIRED=1` reaches
  `AuthorizationConfig::with_session_requirement` through
  `eltanin-agentd`'s `configure_gates`. This superseded the previous
  version of this limitation ("not yet operator-configurable").
- **Critical — the session anchor does not survive the CLI process that
  created it (found by HORO-797 Track B, not by this ticket's own Track
  A suite).** `session_establish_inputs`
  (`crates/eltanin-agent/src/authz/mod.rs`) sets a new session's anchor
  `leader` to the `CreateSession` request's own connecting peer — i.e.
  `eltanin session start`'s own process identity. That process is
  short-lived by design (`crate::session::run`: "establishes it and
  exits"). Every later session-touching operation re-collects that same
  pid's *current* identity and requires
  `WorkloadIdentity::compare_process` to report `Same` — impossible once
  the anchor process has exited. Confirmed live against real binaries
  (macOS): `eltanin session start` reports `SessionEstablished`; the
  very next `eltanin session list`, a separate real process in the same
  POSIX session, reports no active session. Consequently
  `ELTANIN_AGENT_SESSION_REQUIRED=1` is a **deny-all switch** for any
  real multi-invocation CLI usage today, not the "prove intent once per
  terminal" gate ADR 0009 describes. Track A's `authz_session.rs` does
  not catch this because its `self_peer_context()` test helper is the
  same live test-process object for the whole test — the anchor leader
  never actually dies mid-test there, which is exactly the condition
  every real separate CLI invocation produces. **This is a genuine
  product/security architecture decision, not a QA-scenario workaround
  and not something resolved by this record**: resolving it means
  changing which identity dimension the product anchors session trust
  to (e.g. the real POSIX session leader instead of the connecting
  peer), which per this repo's `.claude/CLAUDE.md` §5 requires a founder
  decision and an ADR 0009 amendment. Full writeup:
  `docs/qa/e2e/B-M2-DEVFLOW.md`. This is why this record's Status line
  above is split rather than a bare PASS.

## AC verification (HORO-795)

- **A long-running authorized workload renews silently while all
  required conditions remain valid.** Already true before this ticket
  (`supervise.rs`, unchanged) — confirmed by
  `authz_renewal.rs::renewal_succeeds_repeatedly_while_every_required_condition_still_holds`
  (F-M1-006-era test, re-verified) and the pre-existing
  `a_same_peer_second_request_lease_mints_an_independent_lease_and_the_old_one_stays_releasable`.
- **A policy/session/resource change prevents subsequent renewal.** Met
  for session (`authz_session.rs::bug_a_a_session_reaped_by_expiry_cascade_revokes_its_leases`,
  which also proves the renewal itself is refused), approval
  (`authz_renewal.rs::renewal_is_refused_after_the_approval_is_forgotten`),
  and resource capability
  (`::renewal_is_refused_after_the_resource_capability_changes`).
  Policy-change-specific renewal refusal is met **only via restart** →
  new `IssuerInstanceId` → `ForeignIssuer` rejection of any stale lease
  — never via live policy-revision tracking (no hot-reload path exists;
  see "Known limitations").
- **Explicit revoke blocks future authorization and has documented
  active-workload semantics.** Already true before this ticket
  (`LeaseIssuer::revoke`, `handle_release_lease`) — this ticket's
  contribution is honestly recording "best-effort device-layer teardown"
  semantics (the `EnforcementResult::Error` fix, see "Independent
  review") rather than asserting success or silently discarding failure.
- **Agent restart/reboot does not convert stale state into unintended
  access.** Already true before this ticket (`ComputeLease` is
  `Serialize`-only, `IssuerInstanceId`-scoped) —
  `authz_lifecycle.rs::a_lease_from_a_prior_agent_instance_does_not_survive_a_restart`
  and `crates/eltanin-core/tests/lease_restart.rs::lease_from_a_prior_issuer_instance_is_rejected_as_foreign`
  are this ticket's contribution as test coverage plus this disclosure,
  not new restart-recovery machinery.
- **Race/property tests cover issue/renew/revoke/expire transitions.**
  `authz_concurrency.rs::concurrent_requests_never_overshoot_max_outstanding_leases`,
  `::concurrent_release_and_request_on_a_shared_resource_never_tears_down_a_live_lease`,
  `::compensating_revoke_never_leaks_a_capacity_slot_under_concurrency`,
  `::concurrent_issue_release_cycles_never_produce_a_duplicate_lease_id`
  — all using real `std::thread::scope` concurrency, not simulated.
- **Offline/failure behavior is documented and deterministic.** Met via
  this ADR's "best-effort revoke, undecorated" and "unbounded renewal in
  the fully-ungated default" disclosures, plus the two fail-open bug
  fixes making the killed-process case actually tear down enforcement
  instead of leaking it (see "Independent review").
- **`RevocationRequirement` gates a grant on the resource actually
  supporting device revoke.** `authz_revocation.rs::revocation_required_refuses_a_grant_when_the_resource_lacks_device_revoke`,
  `::revocation_required_grants_normally_when_the_resource_supports_device_revoke`,
  `::revocation_not_required_is_the_default_and_ignores_missing_device_revoke`
  (default-off, byte-identical to pre-HORO-795 unless a deployment opts
  in), `::a_backend_revoke_error_during_release_is_recorded_not_silently_discarded`,
  `::a_backend_without_device_revoke_still_reports_unsupported_not_none`.
- **F-M2-005 verification record can be evaluated independently.** This
  document.

## Independent review

This ticket's own design pass, not a separate post-merge review, found
two genuine fail-open bugs and one honesty gap, all fixed pre-merge,
each verified by temporarily reverting the fix locally and confirming
the new regression test failed against the pre-fix code before being
confirmed as a real regression test:

1. **Bug A (fail-open, High): a session dying by expiry or anchor-leader
   death never cascade-revoked its leases.** `SessionState::reap`
   (F-M2-001/HORO-791) is documented as returning each reaped session's
   id and associated lease ids "for the caller to revoke at the backend/
   lease-state layer," but both call sites in `authz/mod.rs`
   (`membership_for_peer`, `handle_create_session`) discarded that return
   value entirely. **Fixed**: `SessionState::reap` is now `#[must_use]`;
   both call sites consume the returned `Vec<(SessionId, BTreeSet<LeaseId>)>`
   and cascade via a new `cascade_revoke_leases` helper calling the same
   mechanism explicit termination already used.
   Regression: `authz_session.rs::bug_a_a_session_reaped_by_expiry_cascade_revokes_its_leases`.
2. **Bug B (fail-open, High): a lease that expired unreleased never
   called `backend.revoke()`.** `LeaseState::prune` (the expiry sweep,
   called at the top of both `RequestLease` and `ReleaseLease` handling)
   drops an expired lease's record via `HashMap::retain` and holds no
   `ComputeBackend` reference — it structurally could not call `revoke`,
   and neither call site compensated. Concrete consequence: if the
   controlling `eltanin run` process is killed (SIGKILL, a case
   `CLI_CONTRACT.md` already acknowledges as possible), the workload
   could keep running with live backend-side enforcement indefinitely
   after its lease silently expired and was pruned. **Fixed**: new
   `LeaseState::sweep_expired(now)` (`#[must_use]`) plus a new private
   `AuthorizationHandler::sweep_expired_leases` that takes the lock,
   sweeps, drops the lock, then calls `backend.revoke()`; called at the
   top of both `handle_request_lease` and `handle_release_lease`.
   Regression: `authz_lifecycle.rs::bug_b_an_expired_lease_releases_backend_enforcement_via_the_sweep`.
3. **Honesty gap (not a fail-open, Medium): a real backend-revoke error
   was silently mapped to `None`.** `handle_release_lease` mapped a real
   `Err(BackendError)` from `backend.revoke()` to `.ok()` → `None`,
   indistinguishable from the legitimate `None` produced when no teardown
   should be attempted at all. **Fixed**: matched explicitly —
   `Err(error) => Some(EnforcementResult::Error { message: error.to_string() })`
   instead of `.ok()`'s silent `None`, reusing the existing
   `EnforcementResult::Error` variant. Verified by a dedicated regression
   alongside `FakeBackend::revoke`'s already-correct
   `Unsupported{DeviceRevoke}` path:
   `authz_revocation.rs::a_backend_revoke_error_during_release_is_recorded_not_silently_discarded`.

A doc-comment overclaim was also found and fixed: `session_state.rs`'s
module doc previously asserted a not-yet-reaped dead session "can never
be used, because `membership` would independently reject it" — true for
anchor-liveness, false for time-based expiry (`membership` takes no
`now` parameter and never checks `expires_at`). Corrected to state the
actual safety property: `membership_for_peer` calls `reap` immediately
before session lookup, under the same lock.

## Known limitations (carried forward, not silently closed)

- **Most of this ticket's Acceptance Criteria were already true before
  this ticket started.** Its real, verifiable contributions are the two
  fail-open bug fixes and the one honesty fix above, plus new test
  coverage and honest documentation — not new restart-recovery
  machinery.
- **"Best-effort" backend revoke, undecorated.** Lease-layer revocation
  is structural and always succeeds; device-layer teardown outcome
  (including `Unsupported{DeviceRevoke}` and a real `BackendError`) is
  now recorded rather than silently discarded or asserted. This proves
  **nothing** about whether a real NVIDIA backend can actually invalidate
  an already-open device handle on real hardware —
  **`BLOCKED_ON_E3`/`UNVERIFIED_ON_BARE_METAL`**, the same register as
  every prior MVP 2.0 revocation-adjacent claim.
- **Unbounded renewal in the fully-ungated default.** `max_session_ttl`
  bounds renewal only when sessions are required; a deployment requiring
  no session (MVP 1.0 default) gets no cumulative renewal bound at all,
  by its own configuration choice.
- **Policy change requires an agent restart to take effect.** No
  hot-reload path exists (`load_policy` runs once at startup;
  `PolicySet` held immutably for process lifetime). Satisfied only via
  restart → `ForeignIssuer` rejection of any stale lease — not
  continuous policy-drift detection, and must not be read as such.
- **Renewal is not distinguishable from a first grant in the audit
  stream.** An operator must correlate a `Granted{new}` with the
  immediately-preceding `Released{old}` from the same peer. Accepted
  as-is; a client-asserted `supersedes` field was rejected.
- **Lease expiry itself emitted no dedicated audit event as of this
  ticket** — a named forward obligation, closed by F-M2-006/HORO-796
  (see `F-M2-006.md`'s AC verification for `RecordedAgentEvent::LeaseExpired`).
- **No new Feature Verification Record was produced by any of
  HORO-791–794 individually** — `qa_governance_sync.rs` hardcoded
  `FEATURE_IDS` to `F-M1-001..010` only until this PR generalized it;
  adding an unguarded `F-M2-005.md` in isolation would have been
  inconsistent with all four sibling MVP 2.0 tickets before this record
  and the sync-check generalization landed together.

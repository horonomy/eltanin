## AC verification (HORO-833)

- **Spoof-prone fields cannot independently produce trusted identity.**
  `identity_adversarial.rs::self_asserted_claim_never_compares_equal_to_the_same_kernel_observed_value`
  pins that `Evidence<T>`'s `PartialEq` includes `source`, so a
  self-asserted claim can never be indistinguishable from a
  kernel-observed reading of the same value. There is no boolean
  "trusted" accessor anywhere in `eltanin-core::identity` — every
  consumer must inspect the actual `EvidenceSource`.

  Independent review of an earlier revision of this PR found that this
  property held for `Evidence<T>` equality in isolation but **not** for
  `WorkloadIdentity::compare_process` — the one function that actually
  decides identity continuity, which compared only `process_start`'s
  `value` and ignored `source`. A `SelfAsserted` claim whose value
  happened to match a real `KernelObserved` reading would have been
  reported `Same`. Fixed in `compare_process` itself (it now requires
  neither side's `process_start` to be `SelfAsserted`, treating that
  case as `Indeterminate`), with a dedicated regression test:
  `identity_adversarial.rs::self_asserted_start_token_matching_the_real_value_is_not_reported_same`.
  Not exploitable through any code shipped so far (`eltanin-linux`'s
  collector only ever emits `KernelObserved`), but real for the
  `policy`/`lease` consumers F-M1-004/005 will build on this type.
- **PID reuse/exit races fail safely.**
  `identity_adversarial.rs::pid_reused_by_unrelated_process_is_reported_different_not_same`
  and `::process_exit_race_reports_indeterminate_not_a_confirmed_answer`
  cover both cases at the type level. At the collector level,
  `linux_integration.rs::exited_child_process_reports_missing_or_a_genuinely_different_process`
  spawns and reaps a real child process on Linux CI and confirms
  collecting on its stale PID never panics and never fabricates the
  exited process's identity.
- **Missing evidence behavior is regression-tested.**
  `identity_adversarial.rs::missing_evidence_never_reports_present_or_yields_a_value`
  pins `Evidence::is_present()`/`value()` against ever treating
  `Missing`/`Unsupported` as present. `provenance_golden.rs::provenance_record_preserves_missing_and_unsupported_evidence_verbatim`
  confirms this survives a full serialize/deserialize round trip.
- **Audit-ready provenance fixture is reproducible.**
  `eltanin_core::provenance::ProvenanceRecord` links an `ExecutionContext`
  to the `ComputeRequest` it accompanied (the composition seam
  `ComputeRequest`'s own docs call for). `provenance_golden.rs` round-trips
  a fixture through JSON and asserts byte-for-byte reconstruction
  (`provenance_record_round_trips_through_json`) and exact request
  linkage (`provenance_record_links_the_exact_request_it_was_built_with`).
- **F-M1-003 Feature Verification Record references tests/docs.** This
  document.

## Known limitations (carried forward honestly, not silently closed)

- **Ancestry-walk truncation is indistinguishable from reaching the top
  of the process tree** (HORO-832 review finding): if an ancestor's
  `/proc` entry is unreadable (e.g. owned by another UID), the returned
  ancestor list is simply shorter, with no marker for "stopped early."
  Closing this needs a contract change in `eltanin-core`
  (`ProcessAncestor`/`ExecutionContext` have no field for it). Bounded
  impact: ancestry is a contextual signal only, never an authorization
  basis (North Star invariant 4), so this can only degrade an audit
  trail, never a security decision. Tracked in
  `docs/architecture/domain-model.md`.
- **`executable_hash` is never computed** — deliberately, documented
  scope decision (unbounded per-collection cost), not a gap being
  silently carried.
- **No real hardware validation.** All of the above is validated on
  GitHub's `ubuntu-latest` CI runner (a real Linux kernel, real `/proc`),
  which is sufficient for this Feature's scope (plain process
  introspection, no GPU/NVIDIA dependency). It has not been validated on
  the bare-metal Linux/NVIDIA host required by HORO-772's final MVP 1.0
  READY gate — that gate applies to the full vertical slice, not to this
  Feature in isolation, and remains tracked in
  `docs/development/campaign-state.md`.

## Verdict

F-M1-003 is functionally complete for MVP 1.0's hardware-independent
scope: the trust contract, the real Linux collector, and adversarial
regression coverage all exist and pass on CI. **PASS**, with the two
documented limitations above carried forward rather than closed.

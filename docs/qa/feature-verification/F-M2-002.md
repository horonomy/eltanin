## AC verification (HORO-792)

- **A stable workload/context, once approved, does not re-prompt on
  restart.** `authz_approval.rs::remember_admits_a_restarted_workload_without_reprompting`
  proves a `Remember` disposition silently issues a fresh lease on a
  simulated restart, without a second approval.
- **`allow once` is consumed after a single use.**
  `::once_is_consumed_after_a_single_successful_use` confirms an `Once`
  approval cannot be reused for a second `RequestLease`.
- **A changed launcher (digest) is re-evaluated, never trusted from
  stored bytes.** `::a_changed_executable_digest_is_reevaluated_and_denied`
  — the core safety argument this ticket depends on: even a forged
  on-disk approval entry only buys the right to *reach* `PolicySet::evaluate`,
  because every `ApprovalBinding` dimension is re-observed fresh from
  the kernel at `recall` time, which a static file cannot supply or
  fake.
- **A different workload cannot reuse another workload's approval.**
  `::a_different_workload_cannot_reuse_another_workloads_approval`.
- **`deny` overrides `remember` for the same launcher, regardless of
  insertion order.** `::deny_overrides_a_remember_for_the_same_launcher`
  mirrors `PolicySet`'s own established deny-overrides convention.
- **`eltanin approve forget` removes a durable approval.**
  `::forget_removes_a_durable_approval`.
- **`eltanin approve list` returns only the calling peer's own
  approvals.** `::list_approvals_returns_only_the_calling_peers_own`.
- **AC4 (container/cgroup half) — interpreter/container cases are
  context-scoped.** The container/cgroup half is real and built:
  `ApprovalBinding::cgroup_path` is compared at `recall` time, reported
  as `ChangedDimension::CgroupPath` on a material change. **The
  interpreter half is not built and is stated here as only partially
  met** — see "Known limitations" below for the three independently
  sufficient structural reasons. `authz_approval.rs::s5_approving_an_interpreter_admits_a_later_invocation_with_a_different_script`
  (HORO-797 adversarial matrix, S5) pins this limitation as a real,
  reproducible test rather than a design-doc claim only.
- **A remembered approval and an active Trusted Compute Session
  requirement are independent, conjunctive gates.**
  `::approval_and_session_requirements_are_independent_both_must_pass`.
- **A deployment that never opts in keeps MVP 1.0/F-M2-001 behavior
  unchanged.** `::default_config_has_approval_not_required_and_no_store_path`
  and `::not_required_grants_an_authorized_request_with_zero_approvals_ever_recorded`
  together prove `ApprovalRequirement::NotRequired` (the only default —
  there is no way to set `Required` without also supplying a store path,
  correct-by-construction) is byte-identical to pre-HORO-792 behavior.
- **F-M2-002 verification record can be evaluated independently.** This
  document.

## Independent review

Folded into this ticket's own design pass rather than a separate
post-merge review pass (consistent with F-M2-001's precedent): the
executable-digest decision explicitly reverses an earlier documented
decision not to hash executable contents, closing the concern that
motivated it (a 256 MiB cap; above it, `Missing` rather than hashing or
blocking). `sha2` was chosen over `blake3` specifically because
`blake3`'s default features pull in unsafe SIMD code, which this
workspace's `#![forbid(unsafe_code)]` invariant would reject. The
HORO-797 adversarial-matrix pass (PR #63) subsequently added S5
(interpreter-script-reuse) as a dedicated regression pinning the
disclosed AC4 gap live, rather than leaving it as design-doc prose only
— see "AC verification" above.

## Known limitations (carried forward, not silently closed)

- **Does not protect against a compromised-but-unchanged binary reusing
  its old approval.** Digest binding only detects on-disk file
  *replacement* — nothing about in-memory compromise (a process
  exploited after launch) or a malicious-but-unmodified program a user
  was tricked into approving in the first place. The digest changing is
  the only signal this mechanism can ever act on.
- **Not a boundary against the same user's other processes.** Any
  same-uid process that reproduces the exact binding facts (same
  launcher path/digest, same cgroup-or-none) satisfies `recall`
  identically — the same class of gap ADR 0009 discloses for session
  membership.
- **The actual workload/script/argv is invisible to this mechanism
  entirely** — this is topology, not a shortcut this ticket took. A
  `python` interpreter approved once admits every script later run
  through that same `python` binary. Structurally impossible today for
  three independently sufficient reasons, all verified against actual
  source: (1) `crates/eltanin-cli/src/sequence.rs` fixes launch stage S4
  (`RequestLease`) strictly before S6 (`SpawnWorkload`) — no stage
  exists to attach a workload identity to the lease request; (2)
  `eltanin-protocol`'s wire types carry no client-declared identity
  field anywhere; (3) `crates/eltanin-audit/tests/redaction.rs`
  mechanically forbids any collector from reading `/proc/<pid>/cmdline`,
  the one kernel source that could reveal an interpreter's argv.
  Confirmed live by `authz_approval.rs::s5_approving_an_interpreter_admits_a_later_invocation_with_a_different_script`
  (HORO-797 adversarial matrix S5). Closing this gap requires a future
  ADR-0005 amendment (workload attestation) and a new ticket — out of
  scope here, disclosed honestly.
- **macOS's launcher digest is `BestEffort`, not `KernelObserved`.**
  This crate's pinned `libproc` (`0.14.11`) has no `/proc/<pid>/exe`-
  equivalent fd; the only path available is `pidpath`'s currently-
  reported executable path, re-read by name — proving "the file at that
  path right now," not "the image that was actually exec'd." A same-uid
  attacker who replaces the on-disk file *after* the process has already
  exec'd it defeats this check on macOS in a way Linux's fd-based
  approach (`/proc/<pid>/exe`) does not.
- **`UNVERIFIED_ON_BARE_METAL`** (this gates lease *issuance*, never
  device access itself) and **`BLOCKED_ON_E3`** (the cgroup/container
  dimension is observed and compared only, never enforced at the
  device/cgroup layer) — both still blocked on unavailable Linux/NVIDIA
  bare-metal hardware.
- **No TTL on durable (`Remember`/`Deny`) approvals.** `eltanin_core`
  structurally cannot read a wall clock (`WallClockTime` lives only in
  `eltanin-audit`, never the reverse dependency); a durable approval is
  invalidated only by material-change detection (`recall`) or explicit
  `eltanin approve forget`.
- **`DOMAIN_SCHEMA_VERSION` 2→3 invalidates every pre-existing durable
  approval** — a deliberate consequence: `PolicySet::provenance()`'s
  `schema_version` is one of `recall`'s compared security-posture
  dimensions, so a security-relevant schema change requires
  re-approval, the same way a policy revision change already does.
- **No runtime-mintable `PolicySet`/`Condition` extension.** An
  `Approval` narrows admission; `PolicySet` alone still decides whether
  a request is ever allowed. Rejected by design, not an oversight.
- **Not yet operator-configurable via `eltanin-agentd`.** No
  `.with_approval_store()` call exists in
  `crates/eltanin-agent/src/bin/eltanin-agentd.rs` as of this writing —
  library-reachable and exercised by every test above, but not yet
  exposed as `eltanin-agentd` environment-variable configuration. No PR
  closing this gap has merged into `next/mvp-2.0` as of this writing.

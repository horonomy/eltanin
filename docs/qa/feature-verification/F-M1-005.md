## AC verification (HORO-837)

- **Expired/replayed/mismatched leases fail deterministically.**
  - Expiry: `lease_expiry.rs::lease_is_valid_strictly_before_expiry`,
    `::lease_is_expired_at_the_exact_expiry_instant` (inclusive boundary
    — a lease's last valid instant is strictly before `expires_at`, never
    including it), `::lease_is_expired_after_expiry_even_with_identical_matching_context`
    (expiry isn't defeated by an otherwise-perfect match).
  - Replay: `lease_golden.rs::compute_lease_source_never_derives_deserialize`
    — `ComputeLease` is `Serialize`-only, so a serialized lease cannot be
    turned back into one at all; there is no code path to "replay" it
    through this crate's public API. Hardened during HORO-836's
    independent review to scan every stacked `#[derive(...)]` attribute
    and reject a hand-written `impl Deserialize`, not just the single
    nearest derive line.
  - Mismatch: `lease_binding.rs` covers resource, action, pid-only,
    start-token-only, and in-place-`execve()` mismatches, each mapped to
    its own `LeaseValidity` variant (`ResourceMismatch`, `ActionMismatch`,
    `WorkloadMismatch`, `ExecutableMismatch`) rather than a single opaque
    "invalid."
- **Scope broadening is impossible through public APIs/serialization.**
  `lease_expiry.rs::narrow_expiry_to_a_later_instant_is_a_no_op` proves
  `narrow_expiry`'s `min`-only guarantee holds even when the caller
  passes a strictly later instant — there is no public constructor, no
  `&mut` accessor, and (per the replay evidence above) no `Deserialize`
  path either, so nothing outside `LeaseIssuer::issue` can produce or
  widen a `ComputeLease` value.
- **Restart does not resurrect stale privilege.**
  `lease_restart.rs::lease_from_a_prior_issuer_instance_is_rejected_as_foreign`
  — a new `LeaseIssuer` (new `IssuerInstanceId`, as a real agent restart
  would produce) cannot validate any lease from the prior instance, full
  stop. `::revoked_lease_is_rejected_even_when_otherwise_still_valid` and
  `::revoking_an_already_revoked_lease_reports_already_revoked` confirm
  revocation state isn't silently forgotten mid-process either.
  `lease_renewal.rs`'s three tests cover the adjacent renewal-boundary
  case explicitly: re-issuing after expiry mints a **distinct** `LeaseId`
  rather than reusing the expired one
  (`re_issuing_after_expiry_mints_a_distinct_lease_id_not_a_continuation`),
  the expired lease stays expired once a sibling is renewed
  (`the_expired_lease_stays_expired_after_a_sibling_is_renewed`), and
  revoking the renewed lease does not revoke the one it replaced
  (`revoking_a_renewed_lease_does_not_revoke_the_lease_it_replaced`) —
  together proving "renewal" is always a fresh, independent
  authorization act, never a mutation or extension of prior state.
- **Tests map into F-M1-005 verification record.** This document.
- **User docs accurately describe lifetime/renewal limitations.**
  `docs/architecture/domain-model.md`'s "Compute Lease" section documents
  time-injection rationale, validation check order (including the
  review-driven `compare_executable` check), the restart/replay table,
  and two explicitly named known limitations (F-M1-006 dependency on
  `validate`'s `presented`/`now` sourcing; `narrow_expiry`'s shared-
  `LeaseId` limitation) — carried forward below rather than silently
  dropped.

## Known limitations (carried forward, not silently closed)

- **`LeaseIssuer::validate`'s `presented`/`now` are caller-supplied — a
  contract on F-M1-006, not a property of this crate alone.**
  `ProvenanceRecord` and `MonotonicTime` are both `Deserialize`, so
  nothing in `eltanin-core` stops a caller from fabricating either. The
  parent invariant ("possession of serialized lease data alone must not
  silently prove caller identity") depends on F-M1-006's agent sourcing
  `presented` from its own collector and `now` from its own clock, never
  from anything a client sends over IPC. Named explicitly in `lease.rs`
  module docs and `domain-model.md` for this reason; not this ticket's to
  close.
- **`narrow_expiry` does not mint a new identity.** Two `ComputeLease`
  values can share a `LeaseId` with different `expires_at` after
  narrowing. Both would appear in an audit stream (F-M1-009) without a
  way to attribute a compute event to one specifically. Accepted for MVP
  1.0 — narrowing restricts one existing authorization rather than
  minting a new one, and revoking the id invalidates every value sharing
  it — following the same documented-not-silent pattern as
  `eltanin-linux`'s ancestry-truncation gap (HORO-832) and `policy`'s
  revision-immutability gap (HORO-834).
- **No hardware-backed enforcement exists yet.** F-M1-005 defines the
  lease *domain type and its validation rules*; whether a real backend
  actually consults `LeaseValidity` before granting hardware access is
  F-M1-007's scope (hardware-gated, not yet started).

## Verdict

F-M1-005 is complete for MVP 1.0's hardware-independent scope: the lease
domain type, its issue/validate/revoke/narrow lifecycle, and adversarial
regression coverage for expiry, replay, mismatch (resource/action/
workload/executable), restart, and renewal all exist and pass on CI.
**PASS**, with the three documented limitations above carried forward
rather than closed.

## AC verification (HORO-840)

- **End-to-end local request works with Fake Backend.**
  `authz_grant.rs::an_authorized_request_is_granted_end_to_end_with_the_fake_backend`
  exercises the full `AuthorizationHandler` path against a real
  `eltanin_backend::fake::FakeBackend`. `authz_end_to_end.rs` (Linux-only,
  this repo's `ubuntu-latest` CI runner) additionally exercises the whole
  stack — real `UnixStream`, real `SO_PEERCRED`-derived peer credential,
  through `serve_connection`, into a real `AuthorizationHandler` — over
  an actual socket, not a stub `PeerContext`.
- **Unauthorized request cannot mint a valid lease.**
  `authz_grant.rs::a_request_denied_by_policy_cannot_mint_a_lease`,
  `::an_empty_policy_denies_every_request` (default-deny),
  `::a_non_authorizable_peer_is_denied_never_evaluated_against_policy`
  (a `CredentialDivergence`/`Indeterminate` peer is denied before policy
  is ever consulted — `peer.authorizable()` is the gate, never
  `peer.observed()` directly), `::a_backend_lacking_enforce_capability_never_grants_a_lease`
  and `::a_capability_downgrade_leaves_no_lease_available_to_release_later`
  (a capability downgrade never masquerades as a grant, and the
  compensated lease is provably unreleasable afterward — nothing was
  ever inserted into the store).
- **Backend/policy/lease errors fail safely and remain explainable.**
  `authz_backend_failure.rs` covers a scripted `Denied`/`Error`
  enforcement outcome (never grants, compensates the issued lease),
  `resource_disappearing_mid_session_fails_safely`, and
  `releasing_one_of_two_leases_on_the_same_resource_does_not_tear_down_the_others_enforcement`
  (the conditional-backend-revoke guard). "Explainable" is discharged by
  `eltanin-agent::authz::event::AuthorizationEvent` — full internal
  fidelity (which `DecisionReason`/`LeaseError`/`BackendError`/
  `EnforcementResult`/`LeaseValidity` actually applied) recorded once per
  request, entirely off the deliberately-lossy wire response; `ErrorCode`
  itself carries no free-text detail by design (see
  `docs/product/SECURITY_MODEL.md`), so this seam — not the wire — is
  where "remains explainable" is actually true. F-M1-009 (Audit & Explain,
  not yet started) owns turning it into a persistent trail.
- **Restart/disconnect behavior has integration tests.**
  `authz_lifecycle.rs::a_lease_from_a_prior_agent_instance_does_not_survive_a_restart`
  (a fresh `AuthorizationHandler` = a fresh `IssuerInstanceId` + empty
  store, exactly what a real agent restart produces),
  `::a_lease_survives_multiple_independent_calls_without_being_released`
  (disconnect ≠ revocation — lease lifetime is bound to TTL, never to
  connection lifetime, matching HORO-839's one-request-per-connection
  transport), `::an_expired_lease_is_pruned_and_no_longer_releasable`,
  `::a_request_beyond_max_outstanding_leases_fails_safely_without_granting`,
  `::an_expired_leases_slot_is_reclaimed_by_prune_before_the_capacity_check`.

## The `docs/product/SECURITY_MODEL.md` named obligation, discharged

`ReleaseLease` names another lease by id; `LeaseIssuer::revoke` alone
only checks issuer identity and sequence range (enumerable), so nothing
in `eltanin-core` alone stops a client from naming a lease it doesn't
own. `AuthorizationHandler`'s release path calls `LeaseIssuer::validate`
(which itself performs `compare_process` then `compare_executable`, both
required `Same`) before ever calling `revoke`:
`authz_release.rs::a_different_client_cannot_release_another_clients_lease`
(cross-client, distinct pid/start token, same uid — the real-world
attack this obligation names) and
`::an_execve_substitution_is_refused_even_with_the_same_pid_and_start_token`
(same pid/start token, different executable — the substitution
`compare_process` alone cannot see) both confirm `Refused`, and both
confirm the response is **identical** to `releasing_an_unknown_lease_id_is_refused`'s
— a client cannot distinguish "not yours" from "doesn't exist" from
"already released" from the wire alone.

## Known limitations (carried forward, not silently closed)

- **Lease binding subject is the connecting peer process, not a
  cgroup**, decided in this ticket (see
  `docs/architecture/domain-model.md`'s "Local authorization agent
  integration" section). F-M1-007's cgroup-scoped device-BPF enforcement
  must reconcile a process-bound lease with cgroup-scoped enforcement;
  adding a cgroup dimension to `LeaseIssuer::validate` later is additive,
  not a breaking change to what this ticket ships.
- **No expiry-driven backend teardown.** Only an explicit `ReleaseLease`
  calls `backend.revoke`; a lease that expires unreleased leaves
  enforcement applied indefinitely. Fail-closed (over-restrictive), not
  fail-open — F-M1-007's obligation to close with real device state.
- **`eltanin run` must connect as the workload process itself.** Because
  the lease binds to the connecting peer, a CLI that connects and then
  forks the workload would bind the lease to the CLI, which then exits —
  a named cross-ticket obligation on F-M1-008.
- **`eltanin-agentd` always constructs a `FakeBackend`.** F-M1-002's real
  NVIDIA backend does not exist yet; swapping it in is additive once it
  does, not a redesign of this ticket's daemon composition.
- **`LeaseIssuer`'s `revoked: BTreeSet<u64>` has no pruning API**
  (carried forward from HORO-839's design notes) — grows linearly with
  successful issues over the agent's lifetime. Accepted for MVP 1.0's
  single-workstation scope; a compaction API is F-M1-005/HORO-822's to
  add before a long-lived multi-tenant deployment.
